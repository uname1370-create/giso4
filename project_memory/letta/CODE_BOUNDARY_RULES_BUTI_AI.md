# قوانین مرز کد: Buti AI / آینه زیبایی گیسو

وضعیت: قانون معماری و محافظت از ساختار Giso. این سند خودش کد اجرایی نیست.

هدف: وقتی آینه زیبایی گیسو، مخصوصاً سناریوی «آینه ابرو گیسو»، پیاده‌سازی می‌شود، هر کد دقیقاً جای خودش باشد و به ساختار فعلی Giso صدمه نزند.

---

## 1. قانون اصلی

قابلیت آینه زیبایی باید یک ماژول مشخص و محدود داشته باشد:

```text
giso/buti_ai/
```

هر چیزی که مخصوص آینه زیبایی است، باید اول در همین محدوده طراحی و پیاده‌سازی شود.

معنی عملی:

- routeهای آینه زیبایی اینجا باشند.
- serviceهای آینه زیبایی اینجا باشند.
- state/session اختصاصی آینه زیبایی اینجا مدیریت شود.
- orchestration تحلیل، prompt، fallback و preview اینجا باشد.
- template/static اختصاصی آینه زیبایی تا حد ممکن زیر همین ماژول باشد.
- اگر فایل عمومی لازم شد، فقط برای اتصال نازک تغییر کند، نه برای پخش منطق.

---

## 2. قانون «هر کد جای خودش»

قبل از نوشتن هر فایل یا تغییر هر فایل، باید مشخص شود آن کد مالک کدام مسئولیت است.

### داخل `giso/buti_ai/`

مجاز برای:

- ویزارد آینه زیبایی،
- سناریوهای ابرو و خدمات آینده،
- session و state آینه،
- prompt orchestration،
- fallback/demo مخصوص آینه،
- template و static اختصاصی،
- اتصال کنترل‌شده به AI provider و مراکز زیبایی.

### خارج از `giso/buti_ai/`

فقط در صورت ضرورت و با کمترین تغییر مجاز است:

- register کردن blueprint،
- استفاده از helperهای upload/analysis موجود،
- فراخوانی AI providerهای مشترک،
- لینک یا API کنترل‌شده به مراکز زیبایی/رزرو،
- استفاده از panel/history در مرحله‌های بعد.

هیچ منطق محصولیِ آینه زیبایی نباید در فایل‌های عمومی پخش شود.

---

## 3. محدوده‌های ممنوع یا محافظت‌شده

تا وقتی کاربر صریحاً اجازه نداده، این بخش‌ها برای آینه زیبایی تغییر نکنند:

```text
web/
bot_edu/
main.py
giso/bot.py
```

همچنین نباید مسیرهای فعلی تحلیل مو/پوست یا flowهای موجود Giso خراب شوند.

---

## 4. قوانین اتصال به ماژول‌های موجود Giso

### `giso/analysis.py`

مجاز:

- خواندن و reuse الگوی upload/validation،
- استفاده از helper مشترک اگر واقعاً موجود و مناسب است.

غیرمجاز:

- اضافه کردن flow اصلی آینه ابرو داخل این فایل،
- مخلوط کردن سناریوی آینه با تحلیل‌های فعلی.

### `giso/ai_brain.py`

مجاز:

- استفاده از provider/vision call موجود.

غیرمجاز:

- قرار دادن promptهای کامل آینه ابرو و logic تصمیم‌گیری محصول داخل این فایل.

### `giso/beauty_centers/`

مجاز:

- نمایش مراکز مرتبط،
- لینک رزرو یا ثبت lead بعد از نتیجه.

غیرمجاز:

- انتقال wizard یا تحلیل آینه زیبایی به این ماژول.

### `giso/prompts/`

مجاز:

- نگه‌داری فایل prompt اگر convention فعلی Giso همین باشد.

شرط:

- نام فایل‌ها باید واضحاً مربوط به `buti_ai` باشد.
- مصرف و orchestration prompt همچنان در `giso/buti_ai/` بماند.

---

## 5. قانون کمترین اثر جانبی

هر تغییر باید کمترین اثر ممکن روی Giso داشته باشد.

قبل از هر تغییر کدنویسی باید پرسیده شود:

1. آیا این کد واقعاً مخصوص Buti AI است؟
   - اگر بله، باید داخل `giso/buti_ai/` باشد.
2. آیا این تغییر یک اتصال عمومی لازم است؟
   - اگر بله، باید بسیار کوچک، قابل توضیح و بدون تغییر رفتار قبلی باشد.
3. آیا ممکن است flow فعلی Giso را بشکند؟
   - اگر بله، اول طراحی/تست لازم است و بدون اطمینان نباید انجام شود.
4. آیا این کار خارج از محدوده سناریو است؟
   - اگر بله، انجام نشود مگر کاربر صریحاً تأیید کند.

---

## 6. قانون ترتیب اجرا

هیچ مرحله‌ای نباید جلوتر از مرحله قبلی اجرا شود:

1. ثبت Project Memory و سناریو.
2. ثبت طراحی فنی MVP.
3. ثبت قوانین مرز کد و مالکیت ماژول.
4. پیاده‌سازی wizard پایه فقط داخل `giso/buti_ai/`.
5. اضافه کردن تحلیل AI با اتصال کنترل‌شده.
6. اضافه کردن preview یا fallback.
7. اتصال به مراکز زیبایی/رزرو.
8. پنل، آمار، wallet و توسعه‌های بعدی.

---

## 7. معیار قبول هر PR/commit مربوط به Buti AI

هر commit مربوط به آینه زیبایی باید این شروط را داشته باشد:

- فایل‌های اصلی feature زیر `giso/buti_ai/` باشند.
- تغییرات خارج از `giso/buti_ai/` کم، ضروری و قابل توضیح باشند.
- `web/`, `bot_edu/`, `main.py`, `giso/bot.py` بدون مجوز صریح تغییر نکرده باشند.
- مسیرهای فعلی Giso شکسته نشده باشند.
- هیچ secret/API key/credential ذخیره نشده باشد.
- fallback مناسب برای خطای AI وجود داشته باشد.
- اگر preview تصویری اضافه شد، فقط محدوده مجاز صورت/ابرو را تغییر دهد و هویت چهره را حفظ کند.
