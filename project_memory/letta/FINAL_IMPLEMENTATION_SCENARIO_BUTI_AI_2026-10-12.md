# سناریوی نهایی پیاده‌سازی Giso4

**موضوع:** چهار خدمت آینه زیبایی، providerها، حالت قطع اینترنت، صفحه سالن، پنل کاربر، ربات بله، هزینه و مقیاس‌پذیری
**مخزن بررسی‌شده:** `giso4`
**شاخه:** `arena/7f567e47-giso4`
**commit بررسی‌شده:** `03f3733`
**تاریخ:** ۲۰۲۶-۱۰-۱۲

## تصمیم نهایی در یک نگاه

1. چهار خدمت نهایی: **ابرو، لب، رژگونه و خط چشم**.
2. نام محصولی رژگونه: **پیش‌نمایش رژگونه و فرم‌دهی گونه در میکاپ**؛ نه خدمت مستقل آرایش دائم.
3. ابرو و لب در مسیر اصلی AI/inpainting قرار می‌گیرند.
4. رژگونه و خط چشم در نسخهٔ اول با renderer محلی و mask هندسی کنترل‌شده شروع می‌شوند. بعداً در صورت موفقیت به provider متصل می‌شوند.
5. در صورت قطع اینترنت، سایت همچنان می‌تواند **پیش‌نمایش محلی غیرمولد** ارائه کند؛ اما نباید آن را نتیجهٔ واقعی AI معرفی کند.
6. Cloudflare مسیر فعلی و fallback اول باقی می‌ماند. AvalAI به‌عنوان provider ایرانی API تصویری به‌صورت adapter اضافه می‌شود. هوشا فعلاً بدون API عمومی مستند، provider مستقیم نیست.
7. هیچ درخواست AI نباید بدون quota، ledger هزینه، idempotency و قفل مصرف اجرا شود.
8. تجربهٔ اصلی کاربر در سایت باشد؛ ربات بله برای اعلان، پیگیری، رزرو، پشتیبانی و ورود سریع به صفحهٔ نتیجه استفاده شود، نه برای اجرای پردازش سنگین عکس در همان webhook.

# بخش اول — معماری هوش مصنوعی و providerها

## وضعیت واقعی فعلی پروژه

در کد فعلی زیرساخت مهمی وجود دارد:

- `giso/ai_models_registry.py`، رجیستری providerهای خارجی و ایرانی را نگه می‌دارد.
- Cloudflare سه اسلات failover دارد و مدل inpainting زیر در رجیستری ثبت شده است:

```text
@cf/runwayml/stable-diffusion-v1-5-inpainting
```

- `giso/buti_ai/ai_models.py` برای تصویر آینه یک task مشترک دارد:

```text
mirror_image_design
```

و برای آن سه priority/fallback slot پشتیبانی می‌شود.

- AvalAI در رجیستری فعلی وجود دارد، اما فعلاً به‌عنوان provider عمومی vision/text ثبت شده و `image_models` اختصاصی آن برای مسیر آینه کامل نشده است.
- در پنل مدیریت AI، افزودن provider، فعال/غیرفعال‌کردن، تست سلامت، refresh مدل‌ها، failover، مدل آینه و اعتبار کاربر وجود دارد.
- در `giso/buti_ai/generic_service.py`، خدمات عمومی از `SERVICE_MODULES` بارگذاری می‌شوند؛ بنابراین برای رژگونه و خط چشم نباید blueprint مستقل و موازی ساخته شود.
- ربات اصلی در `giso/bot.py` از endpoint بله استفاده می‌کند و منوی callback، پنل AI، رزرو مرکز و اعلان‌ها را از قبل دارد.
- پنل صاحب مرکز در `giso/beauty_centers/templates/beauty_centers/owner_dashboard.html` تب‌های وضعیت، اطلاعات و تصاویر، خدمات، پیام‌ها و نوبت‌ها را دارد.

## مقایسهٔ مسیرهای قابل استفاده

| مسیر | کیفیت مورد انتظار | هزینه | تحمل قطعی اینترنت ایران | پشتیبانی mask/inpainting | تصمیم |
|---|---|---:|---|---|---|
| **Cloudflare Workers AI** | متوسط برای مدل inpainting فعلی؛ باید با عکس واقعی benchmark شود | سهم رایگان روزانه، سپس دلاری | متوسط؛ به مسیر شبکه و اکانت Cloudflare وابسته | بله برای مدل ثبت‌شده | مسیر فعلی و fallback اول |
| **AvalAI** | وابسته به مدل انتخاب‌شده؛ امکان استفاده از مدل‌های تصویر قوی | ریالی/اعتباری، قیمت مدل‌محور | خوب‌تر برای کاربر ایرانی؛ تضمین قطعی نیست | طبق مستندات، `/v1/images/edits` و mask دارد | adapter ایرانی اصلی |
| **Hoosha** | مدل‌های متنوع و رابط فارسی | اشتراک/اعتبار کاربری؛ API سروری عمومی در بررسی پیدا نشد | مناسب در محیط کاربری خودش | image-to-image اعلام شده، قرارداد API/mask عمومی تأیید نشده | فعلاً benchmark و مذاکره، نه provider مستقیم |
| **OpenAI مستقیم** | بالا، مخصوصاً حفظ جزئیات در مدل‌های جدید | مثلاً GPT Image 1.5 از حدود ۰٫۰۰۹ تا ۰٫۲ دلار برای خروجی 1K، جدا از هزینهٔ ورودی تصویر | ضعیف‌تر از مسیر ایرانی و نیازمند مسیر دسترسی پایدار | بله، اما mask کاملاً الزام‌آور نیست | فقط اگر مسیر پرداخت و اتصال پایدار باشد |
| **مدل محلی روی سرور** | وابسته به GPU، مدل و tuning | هزینهٔ زیرساخت؛ هزینهٔ هر درخواست پایین‌تر از API پس از راه‌اندازی | عالی پس از دانلود مدل | بله برای مدل‌های inpainting محلی | فاز بعد؛ نه شرط MVP |

قیمت Cloudflare در مستندات رسمی برابر **۰٫۰۱۱ دلار برای هر ۱۰۰۰ Neuron** اعلام شده و سهم رایگان روزانه **۱۰٬۰۰۰ Neuron** است؛ در پلن Free پس از سهم روزانه، عملیات بیشتر نیازمند Paid plan است.[1]

AvalAI در صفحهٔ تعرفه اعلام می‌کند که API بر مبنای مدل و توکن/مصرف قیمت‌گذاری می‌شود و بسته‌های اعتباری آن می‌تواند اعتبار اضافه بدهد. قیمت نهایی مدل تصویر باید از پنل توسعه‌دهندگان در زمان فعال‌سازی خوانده شود؛ مبلغ ثابت و همیشگی در این گزارش اعلام نمی‌شود.[2]

OpenAI در راهنمای رسمی image edit، ارسال تصویر و mask را پشتیبانی می‌کند، اما خود مستندات تصریح می‌کند mask برای مدل GPT Image بیشتر **راهنما** است و مدل الزاماً شکل mask را دقیق رعایت نمی‌کند.[3] بنابراین حتی با provider قوی نیز composite محلی لازم است.

هوشا image-to-image و مدل‌های مختلف تصویر را در محصول کاربری خود معرفی می‌کند، اما در بررسی فعلی public API مستند برای image edit، mask، احراز هویت سروری و SLA پیدا نشد.[4] صفحهٔ راهنمای API هوشا نیز در حد توضیح مفاهیم API است و قرارداد integration برای Giso4 محسوب نمی‌شود.[5]

## پیشنهاد نهایی provider chain

برای `mirror_image_design` این زنجیره را بسازیم:

```text
Slot 1: Cloudflare inpainting
   ↓ timeout / quota / error / quality gate
Slot 2: AvalAI image edit
   ↓ timeout / quota / error / quality gate
Slot 3: local guided renderer
   ↓
نتیجهٔ قابل‌نمایش با برچسب دقیق AI یا non-AI
```

برای رژگونه و خط چشم، ترتیب بهتر در MVP چنین است:

```text
Local controlled renderer
   ↓ اگر کاربر خروجی طبیعی‌تر خواست و quota داشت
Provider image edit داخل mask
   ↓
Composite روی تصویر اصلی
```

**Hoosha** در پنل providerها فقط وقتی اضافه شود که یکی از این مدارک را از خود سرویس بگیریم:

- base URL و endpoint رسمی
- روش احراز هویت
- نمونهٔ multipart یا JSON
- قرارداد mask و alpha
- محدودیت حجم و timeout
- سیاست نگه‌داری عکس چهره
- quota و قیمت API
- SLA یا حداقل راهکار گزارش خطا

استفاده از scraping پنل هوشا، کوکی کاربر یا automation روی UI برای production ممنوع است.

## تغییر لازم در رجیستری و پنل مدیریت AI

### `giso/ai_models_registry.py`

برای AvalAI باید این قابلیت‌ها اضافه شوند:

```python
"image_models": [
    {
        "id": "<model-from-provider-catalog>",
        "image_kind": "openai_image_edit",
        "capabilities": ["image_edit", "mask", "alpha"],
        "is_free": False,
    }
]
```

شناسهٔ مدل نباید حدسی و hardcode شود. از `/models` یا catalog رسمی provider خوانده و در پنل cache شود.

برای هر مدل این metadata لازم است:

- `modality`: image/text/vision
- `image_kind`
- `supports_edit`
- `supports_mask`
- `supports_alpha`
- `supports_reference_image`
- `supports_output_format`
- `estimated_cost_toman`
- `max_input_bytes`
- `timeout_seconds`
- `requires_paid_account`

### `giso/buti_ai/ai_models.py`

ساختار فعلی سه اسلات را حفظ می‌کنیم، اما باید موارد زیر اضافه شود:

- capability check پیش از ذخیرهٔ assignment
- هزینهٔ تخمینی هر مدل
- provider health status
- آخرین موفقیت و آخرین خطا
- زمان circuit breaker
- تفکیک taskهای زیر:

```text
mirror_photo_analysis
mirror_image_design
mirror_output_validation
mirror_local_preview
```

همچنین `SERVICE_IMAGE_TASK_MAP` باید این دو کلید را شامل شود:

```python
"blush": TASK_MIRROR_IMAGE_DESIGN,
"eyeliner": TASK_MIRROR_IMAGE_DESIGN,
```

### `giso/panel/templates/modules/ai.html`

در تب «آینه گیسو» این فیلدها اضافه شوند:

1. مدل اصلی هر خدمت
2. fallback هر خدمت
3. حالت اجرا: `AI / local / hybrid`
4. هزینهٔ داخلی تخمینی
5. حداکثر هزینهٔ روزانهٔ کل
6. حداکثر مصرف هر کاربر
7. وضعیت health provider
8. دکمهٔ تست با عکس نمونهٔ داخلی و بدون عکس کاربر
9. فعال/غیرفعال‌کردن ارسال عکس به provider خارجی
10. مدت نگه‌داری عکس و خروجی

در تب «اعتبار کاربران» مقدار فعلی «هزینه هر درخواست موفق» باید به مدل cost-aware تبدیل شود:

```text
cost_class = local_preview | cloud_low | cloud_medium | cloud_high
provider_cost_toman
user_charge_toman
margin_toman
```

مبلغ کاربر را هرگز مستقیماً از پاسخ provider استخراج و همان لحظه کسر نکنیم؛ ابتدا cost ledger ثبت شود، سپس charge اتمیک اعمال شود.

# بخش دوم — حالت قطع اینترنت و preview بدون AI

## پاسخ دقیق

**بله، تا حد قابل‌قبولی می‌توان preview بدون AI ساخت؛ اما این خروجی «نتیجهٔ هوش مصنوعی» نیست.**

چیزهایی که بدون اینترنت و بدون مدل مولد امکان‌پذیر است:

- تشخیص چهره با MediaPipe اگر مدل محلی قبلاً روی سرور موجود باشد.
- ساخت mask ابرو، لب، چشم و گونه از landmarkها.
- تغییر رنگ لب با blend محلی.
- ساخت سایهٔ رژگونه با gradient و feather.
- کشیدن بن‌مژه و خط چشم با curve/stroke.
- تنظیم شدت، opacity، رنگ و before/after.
- بازگرداندن نتیجه با برچسب `local_preview`.

چیزهایی که بدون AI مولد کیفیت واقعی آن را نمی‌توان تضمین کرد:

- ساخت تار مو و بافت طبیعی ابرو
- ترکیب دقیق رنگ لب با texture واقعی پوست
- ترمیم مرزهای پیچیدهٔ پوست و آرایش
- شبیه‌سازی طبیعی انعکاس، مژه و جزئیات ریز
- خروجی حرفه‌ای که از اجرای واقعی قابل تشخیص نباشد

## fallback محلی هر خدمت

| خدمت | fallback آفلاین | کیفیت مورد انتظار | متن صادقانهٔ UI |
|---|---|---|---|
| ابرو | curve/polygon، پرکردن نرم، opacity و رنگ | پیش‌نمایش فرم، نه بافت مو | «پیش‌نمایش محلی فرم ابرو» |
| لب | تغییر hue/saturation داخل لب و حفظ contour | متوسط برای رنگ | «پیش‌نمایش محلی رنگ لب» |
| رژگونه | دو gradient بیضوی روی گونه و blend در فضای Lab/HSV | خوب برای تصمیم اولیه | «پیش‌نمایش محلی شدت و رنگ» |
| خط چشم | curve روی lash line با antialias و ضخامت محدود | خوب برای مدل ظریف | «پیش‌نمایش محلی خط چشم» |

## وضعیت‌های خروجی

هر generation باید یکی از این statusها را داشته باشد:

```text
ai_generated
local_preview
queued
provider_failed_local_preview
blocked_no_trusted_mask
blocked_quota
blocked_consent
```

در هیچ قالبی نباید `local_preview` با عنوان «طراحی AI نهایی» نمایش داده شود.

## اگر خود MediaPipe نیز در دسترس نباشد

یک fallback دوم می‌تواند crop و anchorهای دستی UI باشد، اما به‌عنوان حالت اضطراری:

- کاربر با دو یا سه drag point ناحیه را مشخص می‌کند.
- سیستم فقط blend محدود انجام می‌دهد.
- نتیجه به‌عنوان preview تقریبی ثبت می‌شود.

این حالت را برای MVP عمومی فعال نکنیم؛ چون تجربهٔ بد و mask اشتباه می‌تواند اعتماد کاربر را کاهش دهد.

## تغییر لازم برای offline

یک ماژول مستقل اضافه شود:

```text
giso/buti_ai/local_preview/
  __init__.py
  renderer.py
  masks.py
  color_ops.py
  quality.py
```

توابع اصلی:

```python
render_local_preview(service_key, image_path, detection, style, change_level)
validate_local_preview(source_path, output_path, mask_path)
```

این ماژول نباید provider را صدا بزند و باید deterministic باشد تا تست و cache قابل اعتماد بماند.

# بخش سوم — صفحهٔ اختصاصی سالن زیبایی و آگهی سالن‌دار

## هدف صفحه

صفحهٔ سالن نباید فقط یک کارت نام و تلفن باشد. باید به سالن‌دار نشان دهد که Giso4 برای او **مشتری قابل‌پیگیری** می‌سازد.

عنوان پیشنهادی:

> **پروفایل حرفه‌ای سالن در گیسو؛ جایی که مشتری قبل از رزرو خدمتش را می‌بیند.**

## طراحی پیشنهادی صفحه عمومی سالن

### بخش ۱ — Hero شیک و کاربردی

- تصویر اصلی واقعی سالن یا نمونه‌کار
- نام سالن، منطقه، شهر و وضعیت تأیید
- برچسب‌های «پاسخ‌گویی سریع»، «رزرو فعال»، «متخصص ابرو» و مانند آن فقط بر اساس دادهٔ واقعی
- CTA اصلی: **مشاهده خدمات و رزرو**
- CTA دوم: **دیدن نمونه‌کارها**
- امکان اشتراک‌گذاری در بله، تلگرام، واتساپ و کپی لینک

### بخش ۲ — نوار اعتماد

فقط دادهٔ قابل اثبات نمایش داده شود:

- تعداد رزرو تکمیل‌شده
- امتیاز و تعداد نظر
- مدت فعالیت، اگر تأیید شده
- وضعیت پاسخ‌گویی
- آخرین بروزرسانی صفحه
- مجوز یا مدرک فقط در صورت بارگذاری و تأیید مدیریت

### بخش ۳ — خدمات به شکل کارت

هر کارت خدمت شامل:

- نام خدمت
- تصویر نمونه‌کار همان خدمت
- توضیح کوتاه
- بازهٔ قیمت
- مدت اجرا
- امکان رزرو
- دکمهٔ «پیش‌نمایش روی عکس من» برای خدمات آینه

برای چهار خدمت:

- ابرو: فیبروز، میکروبلیدینگ، اصلاح و فرم
- لب: شیدینگ و رنگ لب
- رژگونه: میکاپ، گریم، میکاپ عروس
- خط چشم: بن‌مژه، خط نازک، خط چشم دائم

### بخش ۴ — نمونه‌کارهای فیلترشده

در وضعیت فعلی owner dashboard حداکثر سه تصویر عمومی دارد. برای جذاب‌شدن صفحه، این مدل بهتر است:

- تصویر کاور
- ۶ تا ۱۲ نمونه‌کار در سطح هر مرکز، با سقف storage و moderation
- فیلتر بر اساس `service_key`
- برچسب «قبل/بعد» فقط وقتی هر دو تصویر و رضایت وجود دارد
- جلوگیری از استفاده از عکس آینهٔ AI به‌عنوان نمونه‌کار اجرای واقعی
- ثبت alt text و توضیح کوتاه

فیلد فعلی `service_key` در آپلود gallery باید به چهار خدمت جدید نیز مجهز شود:

```text
brow
lip_shading
blush
eyeliner
makeup
```

### بخش ۵ — ابزار پیش‌نمایش اختصاصی سالن

روی هر کارت خدمت:

> **عکس خودت را بفرست و این مدل را ببین**

بعد از preview:

> **رزرو همین خدمت در این سالن**

`final_design_id` و `service_id` باید در لینک رزرو signed/validated باشند و backend دوباره مالکیت و تطابق آن‌ها را بررسی کند.

### بخش ۶ — اطلاعات عملی

- محله و آدرس تقریبی
- نقشه یا لینک مسیریابی
- ساعت کاری
- زمان پاسخ‌گویی
- شماره با دکمهٔ «نمایش تماس» برای ثبت click
- گزینهٔ پیام در سایت
- گزینهٔ شروع گفتگو در بله

### بخش ۷ — پیشنهاد ویژهٔ قابل اندازه‌گیری

سالن‌دار باید بتواند پیشنهاد واقعی تعریف کند:

- تخفیف اولین رزرو
- مشاورهٔ رایگان پیش از شیدینگ
- پکیج ابرو + لب
- میکاپ مناسبتی
- ظرفیت محدود هفته

# بخش پنجم — ربات بله

## واقعیت فنی فعلی

مستندات رسمی بله، API را بر پایهٔ API بات تلگرام معرفی می‌کند. درخواست‌ها از این مسیر انجام می‌شوند:

```text
https://tapi.bale.ai/bot<TOKEN>/METHOD_NAME
```

بله دریافت update با `getUpdates` یا webhook، callback query، دکمه‌های inline، ارسال تصویر و پرداخت wallet را پشتیبانی می‌کند. updateها تا ۲۰۰۰ پیام آخر یا ۲۴ ساعت نگه‌داری می‌شوند، بنابراین webhook باید idempotent باشد و update تکراری را نادیده بگیرد.[6]

کد فعلی Giso4 همین الگو را در `giso/bot.py` استفاده می‌کند و در حال حاضر پنل AI، callback menu، اعلان و رزرو را دارد.

## هدف ربات

ربات نباید نسخهٔ ناقص سایت باشد. باید برای این کارها استفاده شود:

- جذب کاربر
- ورود سریع به preview
- پیگیری رزرو
- اعلان salon
- پاسخ اولیه و FAQ
- بازگرداندن کاربر به نتیجهٔ قبلی
- پشتیبانی و ارتباط دوطرفه

## منوی پیشنهادی کاربر

```text
🪞 آینه زیبایی
📍 پیدا کردن سالن
📅 رزروهای من
✨ پیش‌نمایش‌های من
💬 پیام‌های من
🎁 پیشنهادهای نزدیک من
👤 پروفایل
💳 اعتبار من
🆘 راهنما و پشتیبانی
```

### جریان آینه در ربات

1. کاربر «آینه زیبایی» را می‌زند.
2. خدمت را انتخاب می‌کند: ابرو، لب، رژگونه، خط چشم.
3. ربات توضیح می‌دهد پردازش اصلی در سایت انجام می‌شود.
4. دکمهٔ deep link باز می‌شود:

```text
https://giso.example/buti-ai/eyebrow?source=bale&campaign=bot
```

5. پس از تولید، سایت یک `result_token` کوتاه و یک لینک امن می‌سازد.
6. ربات لینک نتیجه، مرکزهای پیشنهادی و دکمهٔ رزرو را می‌فرستد.
7. در صورت رضایت کاربر، نتیجهٔ کوچک‌شده به‌صورت تصویر نیز ارسال می‌شود؛ فایل اصلی فقط روی سایت خصوصی بماند.

## منوی سالن‌دار

```text
🏥 مرکز من
📊 آمار بازدید و سرنخ
📸 مدیریت نمونه‌کار
🧾 خدمات و قیمت
📅 نوبت‌ها
💬 پیام‌های مشتری
📢 پیشنهاد و تبلیغ
🔗 لینک اختصاصی سالن
🆘 پشتیبانی
```

ربات سالن‌دار باید اجازه دهد:

- اعلان رزرو جدید را تأیید کند.
- پیام آماده برای مشتری بفرستد.
- وضعیت نوبت را قبول/رد/پیشنهاد زمان دیگر کند.
- آمار روزانه را ببیند.
- لینک صفحه و QR را دریافت کند.
- کمپین فعال کند.

ویرایش‌های طولانی، آپلود چندتصویری و مدیریت مالی بهتر است به پنل وب منتقل شود.

## جذب کاربر با ربات

- لینک `start` برای هر سالن و هر کمپین:

```text

```

- بعد از شروع، ربات بلافاصله همان خدمت سالن را نمایش دهد.
- برای هر کمپین referral code ثبت شود.
- دکمهٔ «ارسال به دوست» و «مشاهده نمونه‌کار» داشته باشد.
- اعلان نتیجهٔ آماده با CTA رزرو ارسال شود.
- پیام تبلیغاتی بدون رضایت و ارسال انبوه ناخواسته فعال نشود.

مستندات بله deep link با پارامتر `start` و پرداخت wallet را پشتیبانی می‌کند؛ اگر پرداخت درون‌رباتی فعال شود، مبلغ باید به ریال صحیح تبدیل و webhook پرداخت با payload داخلی تطبیق داده شود.[6]

## کنترل‌های ضروری ربات

- ذخیرهٔ `update_id` و رد duplicate
- صف جدا برای ارسال پیام و عکس
- timeout و retry با backoff
- عدم پردازش تصویر AI داخل handler اصلی
- عدم چاپ token در log
- rate limit برای هر chat/user
- دکمهٔ cancel برای flowهای چندمرحله‌ای
- نگه‌داشتن state در DB یا Redis، نه فقط حافظهٔ process
- webhook امضاشده/secret path و محدودیت IP در صورت امکان
- عدم نمایش raw provider error به کاربر

# بخش ششم — هزینه و مدل پذیرش کاربر و سالن

## مشکل فعلی هزینه

در پنل فعلی هزینهٔ «هر درخواست موفق» وجود دارد. این برای شروع کافی است، اما برای چهار خدمت و چند provider خطرناک است؛ چون یک درخواست ممکن است سه fallback را امتحان کند و هزینهٔ واقعی سه برابر شود.

## ledger لازم

برای هر عملیات این رکورد ذخیره شود:

```text
id

center_id
session_id
service_key
request_id / idempotency_key
provider_name
model_name
attempt_no
status
is_ai_generated
input_bytes
output_bytes
provider_usage_json_minimal
provider_cost_toman
user_charge_toman
created_at
finished_at

```

اطلاعات خام عکس و prompt کامل را در ledger مالی ذخیره نکنیم.

## قانون کسر اعتبار

1. قبل از شروع، یک reservation کوتاه برای حداقل هزینه ایجاد شود.
2. بعد از موفقیت، هزینهٔ واقعی ledger شود.
3. اگر fallback دوم نیز اجرا شد، هزینهٔ هر attempt جدا ثبت شود.
4. اگر provider خطا داد و خروجی موفق نبود، به‌طور پیش‌فرض از کاربر کسر نشود.
5. اگر local preview ارائه شد، cost class آن صفر یا تعرفهٔ بسیار کم باشد.
6. retry خودکار بی‌نهایت ممنوع؛ حداکثر دو attempt خارجی.

## پیشنهاد تعرفهٔ محصولی

قیمت‌های زیر **پیشنهاد محصولی** هستند و باید با هزینهٔ واقعی provider و نرخ تبدیل تنظیم شوند، نه اینکه واقعیت بازار یا قیمت API فرض شوند:

| محصول | پیشنهاد اولیه |
|---|---:|
| اولین preview کاربر جدید | رایگان، یک‌بار برای هر خدمت |
| preview محلی | رایگان یا ۰ تا ۱ اعتبار |
| preview AI سریع | ۲ تا ۵ اعتبار مصرفی |
| خروجی AI باکیفیت | ۶ تا ۱۲ اعتبار مصرفی |
| retry به‌دلیل خطای provider | رایگان |
| تغییر style در همان عکس | نصف هزینهٔ درخواست اول، اگر cache/mask قابل استفاده باشد |

به‌جای نمایش «هزینهٔ API»، کاربر باید اعتبار ساده ببیند. پنل مدیر هزینهٔ واقعی و margin را ببیند.

# بخش هفتم — مقیاس‌پذیری و تحمل ورود هم‌زمان کاربران

## ریسک‌های اصلی

1. Flask worker در زمان generation خارجی block شود.
2. چند کاربر هم‌زمان provider را با retryهای زنجیره‌ای پر کنند.
3. فایل‌های بزرگ عکس RAM و disk را مصرف کنند.
4. SQLite در ثبت هم‌زمان ledger، session و bot قفل شود.
5. دوباره‌فرستادن webhook یا refresh صفحه generation را تکرار کند.
6. یک کاربر با چند حساب quota را دور بزند.
7. هزینهٔ provider بدون سقف افزایش یابد.
8. خروجی‌های شخصی دیگران از طریق filename یا session دیده شود.

## معماری لازم قبل از public launch

```text
Flask web
  ↓ ثبت job و پاسخ سریع 202
Queue: Redis/RQ یا Celery
  ↓
AI worker محدود و قابل اندازه‌گیری
  ├── local preview worker
  ├── Cloudflare adapter
  └── AvalAI adapter
  ↓
Object storage private + signed URL
  ↓
DB status update + notification
```

برای MVP کم‌تعداد می‌توان ابتدا با یک worker process و SQLite/DB فعلی شروع کرد، اما endpoint وب نباید تا پایان generation خارجی باز بماند.

## حداقل کنترل‌های مقیاس

- `job_id` و `idempotency_key` برای هر درخواست
- وضعیت‌های `queued/running/succeeded/failed/expired`
- queue با concurrency محدود، مثلاً ۲ تا ۴ worker شروع
- محدودیت هر کاربر: ۱ job هم‌زمان
- محدودیت کل سایت: بر اساس ظرفیت provider
- timeout خارجی ۳۰ تا ۶۰ ثانیه
- circuit breaker بعد از چند خطای متوالی
- cache بر اساس hash عکس + service + style + change level + model
- resize ورودی به سقف مشخص پیش از ارسال
- حذف EXIF و metadata حساس
- private media و signed URL کوتاه‌مدت
- cleanup job برای عکس‌ها و خروجی‌های منقضی
- metrics: queue depth، p50/p95 latency، success rate، provider error rate، cost/request

## اگر ۱۰، ۱۰۰ یا ۱۰۰۰ کاربر هم‌زمان بیایند

| بار تقریبی | خطر | راهکار لازم |
|---|---|---|
| ۱۰ کاربر هم‌زمان | block شدن request و retry | queue ساده، concurrency محدود، local preview فوری |
| ۱۰۰ کاربر هم‌زمان | قفل DB، exhaustion provider | worker جدا، Redis، cache، rate limit و job status |
| ۱۰۰۰ کاربر هم‌زمان | هزینه و صف طولانی، overload provider | صف durable، چند worker، object storage، autoscaling و quota سراسری |

برای چهار خدمت، باید load test با سناریوی واقعی انجام شود:

- ۱۰، ۵۰ و ۱۰۰ job هم‌زمان
- ۲۰٪ خطای provider
- قطع کامل provider اصلی
- تکرار callback و refresh
- عکس‌های نزدیک سقف حجم
- هم‌زمانی سایت و ربات بله

تا قبل از اجرای این تست‌ها، ظرفیت عددی قطعی اعلام نمی‌کنیم.

# معیارهای پذیرش قبل از عمومی‌سازی

| حوزه | معیار پیشنهادی |
|---|---|
| صحت خروجی | بیرون mask در composite تغییر نکند؛ artifact خارج ROI رد شود |
| AI واقعی | هر خروجی provider واقعی metadata و status داشته باشد |
| offline | local preview بدون provider نمایش داده شود و برچسب درست داشته باشد |
| هزینه | هیچ request موفق بدون ledger و charge policy نماند |
| امنیت | مالکیت فایل، final design و reservation server-side بررسی شود |
| provider | حداقل provider اصلی و fallback تست واقعی شده باشند |
| UX | کاربر در کمتر از چند مرحله به preview و رزرو برسد |
| سالن | سالن بتواند خدمت، قیمت، نمونه‌کار و اعلان را مدیریت کند |
| ربات | duplicate update، retry و صف پیام تست شده باشد |
| مقیاس | load test اجرا و p95 latency ثبت شده باشد |

## گام بعدی قطعی

قبل از طراحی ظاهری کامل یا اتصال مدل‌های بیشتر، این چهار کار را انجام دهیم:

1. **قرارداد provider و cost ledger** را در پروژه تعریف کنیم.
2. **local preview واقعی** برای رژگونه و خط چشم بسازیم.
3. **AvalAI را با یک image edit واقعی و mask آزمایش کنیم.**
4. **feature flag و queue** را برای فعال‌سازی تدریجی چهار خدمت اضافه کنیم.

بعد از موفقیت این چهار مورد، طراحی نهایی صفحه سالن و ربات را به کد تبدیل کنیم. این ترتیب جلوی آن را می‌گیرد که هزینهٔ API، طراحی UI و جذب سالن قبل از اثبات کیفیت خروجی مصرف شود.

# بخش تکمیلی — قرارداد نهایی آپلود، تحلیل و پیشنهاد مدل قبل از خروجی

این بخش در تاریخ 2026-10-12 به سند نهایی اضافه شد تا ایجنت بعدی از وضعیت واقعی فعلی ادامه دهد و مرحله‌ها را دوباره از ابتدا طراحی نکند.

## رفتار قطعی مورد انتظار

برای ابرو و لب، flow باید این ترتیب را داشته باشد:

```text
انتخاب مدل/شدت
→ آپلود عکس
→ preview
→ validate و بررسی کیفیت
→ تحلیل Vision بر اساس عکس + مدل انتخابی + شدت تغییر
→ نمایش دو گزینه: پیشنهاد گیسو / انتخاب دستی کاربر
→ تأیید کاربر با final_style
→ تولید نهایی با همان final_style
→ before/after + وضعیت صادقانه AI/non-AI + دانلود تصویر/PDF
```

POST اول آپلود نباید مستقیماً به صفحه final redirect شود؛ باید candidate را نگه دارد و صفحه پیشنهاد را با status `200` برگرداند. POST دوم با `analysis_confirmed=1` و `final_style` مجاز است به final redirect شود.

## قرارداد داده پیشنهاد

```json
{
  "status": "ai_analyzed | ai_unavailable | local_checked",
  "style": "validated-style-key",
  "label": "نام مدل",
  "reason": "دلیل کوتاه و غیرقطعی",
  "alternatives": []
}
```

برای ابرو، منبع تحلیل `analyze_eyebrow_photo` و برای لب، منبع تحلیل `analyze_lip_photo` است. اگر provider در دسترس نباشد، گزینه انتخاب دستی کاربر فعال می‌ماند و UI نباید fallback محلی را AI واقعی اعلام کند.

## وضعیت واقعی اعمال‌شده در working tree

اتصال اولیه این قرارداد اکنون در فایل‌های زیر اعمال شده است:

- `giso/buti_ai/routes.py`: پاسخ recommendation، candidate مرحله‌ای و confirmation.
- `giso/buti_ai/generic_service.py`: نگه‌داری `ai_analysis` و `recommended_style`.
- `giso/buti_ai/static/buti_ai.js`: درخواست validate بعد از انتخاب فایل، نمایش checkها و کارت دوگزینه‌ای.
- `giso/buti_ai/static/buti_ai.css`: ظاهر کارت تحلیل و انتخاب.
- `giso/buti_ai/templates/buti_ai/eyebrow_wizard.html`: recommendation ابرو.
- `giso/buti_ai/templates/buti_ai/generic_service_wizard.html`: recommendation لب و خدمات عمومی.

این تغییرات هنوز انتشار نهایی محسوب نمی‌شوند؛ تست قدیمی direct-redirect باید مطابق قرارداد جدید اصلاح شود. آخرین failure ثبت‌شده:

```text
test_buti_ai_eyebrow_real_photo_step_flow_with_csrf
expected 302, received 200
```

این failure نشان‌دهنده اختلاف تست قدیمی با رفتار سناریوی جدید است، نه مجوزی برای برگرداندن redirect مستقیم.
