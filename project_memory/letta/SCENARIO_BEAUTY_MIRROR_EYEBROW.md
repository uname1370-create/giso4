# سناریوی محصول: آینه ابرو گیسو

وضعیت: طراحی محصول و حافظه سناریو؛ هنوز کدنویسی Giso شروع نشده است.

هدف: ساخت اولین مسیر ساده و شیک از «آینه زیبایی گیسو» برای خدمت ابرو، داخل خود پروژه Giso و با استفاده از ظرفیت‌های Python/Flask فعلی. کل این قابلیت باید به صورت ماژول مستقل داخل `giso/buti_ai/` بماند و با بخش‌های دیگر Giso قاطی نشود.

---

## 1. تصمیم اصلی محصول

اسم مسیر نباید فقط «میکروبلید» باشد، چون میکروبلیدینگ فقط یک تکنیک خاص است و همه کاربران تفاوت تکنیک‌ها را نمی‌دانند.

اسم پیشنهادی مسیر:

**آینه ابرو گیسو**

زیرعنوان پیشنهادی:

**فرم مناسب ابرو را قبل از انجام، روی چهره‌ات ببین.**

میکروبلیدینگ باید یکی از گزینه‌های داخل مسیر باشد، نه اسم کل مسیر.

---

## 2. اصل معماری ماژولار — پوشه مستقل `giso/buti_ai/`

### قانون سخت مرز کد

این سناریو فقط وقتی مجاز به پیاده‌سازی است که مرز کار آن دقیقاً رعایت شود:

- مالک اصلی کد: `giso/buti_ai/`.
- هر کد باید جای مشخص خودش را داشته باشد.
- کد اختصاصی آینه زیبایی نباید در بخش‌های نامرتبط Giso پخش شود.
- تغییر خارج از `giso/buti_ai/` فقط برای اتصال نازک و ضروری مجاز است.
- بخش‌های `web/`, `bot_edu/`, `main.py`, `giso/bot.py` بدون اجازه صریح تغییر نکنند.
- جریان‌های فعلی Giso، مخصوصاً تحلیل‌های فعلی، نباید آسیب ببینند.
- اگر جای درست یک کد روشن نبود، پیاده‌سازی متوقف شود و از کاربر سؤال شود.

سند کامل قوانین:

```text
project_memory/letta/CODE_BOUNDARY_RULES_BUTI_AI.md
```


این قابلیت نباید به شکل کد پراکنده در کل پروژه پیاده‌سازی شود و نباید یک پروژه جدا بیرون از Giso باشد.

تصمیم قطعی:

- پوشه/ماژول اصلی قابلیت: **`giso/buti_ai/`**
- نام مفهومی/فنی ماژول برای توسعه: **Buti AI / `buti_ai`**
- نام محصول در UI فارسی: **آینه زیبایی گیسو** و برای سناریوی اول **آینه ابرو گیسو**

قواعد معماری:

1. همه چیزهایی که مخصوص آینه زیبایی است باید تا حد ممکن داخل `giso/buti_ai/` باشد:
   - route/blueprintهای آینه زیبایی،
   - serviceهای داخلی سناریو،
   - templateهای اختصاصی،
   - static assets اختصاصی اگر لازم شد،
   - مدل/اسکیما/ذخیره‌سازی اختصاصی اگر لازم شد،
   - promptهای اختصاصی یا wrapperهای prompt، مگر اینکه ساختار فعلی Giso محل رسمی دیگری داشته باشد.

2. فایل‌های عمومی Giso فقط برای اتصال نازک تغییر کنند؛ یعنی فقط در حد:
   - register کردن blueprint،
   - استفاده از AI providerهای موجود،
   - اتصال کنترل‌شده به مراکز زیبایی/رزرو،
   - reuse کردن الگوهای upload/analysis فعلی.

3. نباید منطق آینه زیبایی داخل این بخش‌ها پخش شود:
   - `giso/analysis.py` فقط الگو/زیرساخت یا wrapper مشترک بدهد؛ منطق سناریوی ابرو در `giso/buti_ai/` بماند.
   - `giso/beauty_centers/` فقط برای نمایش مرکز/رزرو استفاده شود؛ منطق آینه داخل آن منتقل نشود.
   - `giso/ai_brain.py` فقط provider/vision مشترک باشد؛ prompt و orchestration سناریو در `giso/buti_ai/` بماند.
   - `web/`, `bot_edu/`, `main.py` برای این سناریو تغییر نکنند مگر با مجوز صریح.

4. اگر بعداً خدمات دیگر مثل لب، پوست، مو یا ناخن اضافه شد، زیر همین ماژول توسعه داده شود، نه با پوشه‌های پراکنده جدید.

5. ترتیب اجرا باید رعایت شود: اول حافظه و سناریو، بعد طراحی فنی، بعد MVP، بعد AI/preview، بعد اتصال عمیق به رزرو و پنل‌ها.

## 4. گزینه‌های ابرو برای شروع

گزینه‌ها باید هم برای کاربر عادی قابل فهم باشند، هم برای سالن/مرکز زیبایی قابل قبول باشند.

1. **طبیعی و نچرال**
   - برای تغییر کم، ظاهر دخترانه و روزمره.

2. **میکروبلیدینگ ظریف**
   - برای ابروی کم‌پشت، تاربه‌تار و طبیعی‌تر.

3. **شیدینگ پودری**
   - برای ظاهر مرتب‌تر، کمی آرایش‌شده‌تر و پرتر.

4. **کامبینیشن**
   - ترکیب میکروبلیدینگ و شیدینگ برای نتیجه کامل‌تر.

5. **نمی‌دانم؛ گیسو پیشنهاد بدهد**
   - گزینه پیش‌فرض و بهترین انتخاب برای کاربران مردد.

## 6. Promptهای پیشنهادی AI

### 6.1 بررسی کیفیت عکس

هدف: تشخیص اینکه عکس برای تحلیل ابرو مناسب هست یا نه.

خروجی باید JSON باشد:

```json
{
  "ok": true,
  "reasons": [],
  "face_visible": true,
  "eyebrows_visible": true,
  "lighting": "good",
  "angle": "front",
  "needs_reupload_message": ""
}
```

قواعد:

- اگر صورت کامل نیست، `ok=false`.
- اگر ابرو واضح نیست، `ok=false`.
- اگر نور خیلی کم است، `ok=false`.
- اگر زاویه خیلی کج است، `ok=false`.

### 6.2 تحلیل ابرو

AI باید بررسی کند:

- فرم کلی صورت
- فاصله چشم‌ها
- حالت فعلی ابرو
- ضخامت ابرو
- قوس ابرو
- تقارن
- مدل پیشنهادی از بین گزینه‌های تعریف‌شده

خروجی پیشنهادی JSON:

```json
{
  "face_shape": "",
  "current_brow_summary": "",
  "recommended_style": "natural | microblading | powder | combination | giso_suggested",
  "change_level": "very_natural | medium | clear",
  "why": "",
  "do": [],
  "avoid": [],
  "alternative_styles": []
}
```

### 6.3 متن نتیجه فارسی

هدف: تبدیل خروجی فنی AI به متن ساده، محترمانه و قابل فهم برای کاربر.

لحن:

- فارسی روان
- دوستانه
- بدون ترساندن کاربر
- بدون ادعای قطعی پزشکی/زیبایی
- کوتاه و شیک

### 6.4 Prompt پیش‌نمایش تصویری

اگر image generation فعال شد:

- فقط ناحیه ابرو تغییر کند.
- چشم، بینی، لب، پوست، فرم صورت و هویت چهره تغییر نکند.
- نتیجه طبیعی و قابل اجرای سالن باشد.
- سبک انتخاب‌شده اعمال شود.
- از اغراق، تغییر چهره، آرایش کامل یا تغییر پوست جلوگیری شود.

نمونه دستور مفهومی:

> Apply a realistic eyebrow design matching the selected style. Edit only the eyebrow area. Keep the face identity, eyes, skin, nose, lips, hair, lighting and background unchanged. The result must look natural and salon-realistic.

## 7. استفاده از ظرفیت فعلی Giso

این سناریو باید داخل خود Giso ساخته شود، نه پروژه جدا؛ اما داخل Giso هم باید **ماژولار و جدا** بماند.

ظرفیت‌های موجود و نقش هرکدام:

- `giso/buti_ai/` — محل اصلی و مالک سناریو. همه routeها، serviceها، templateها، prompt wrapperها، state و منطق آینه زیبایی تا حد ممکن اینجا قرار بگیرد.
- `giso/analysis.py` — فقط الگوی upload/analysis و reuse زیرساخت؛ منطق محصول آینه ابرو نباید در این فایل پخش شود.
- `giso/ai_brain.py` — فقط استفاده از AI providerها و vision call موجود؛ orchestration و prompt سناریو در `giso/buti_ai/` بماند.
- `giso/prompts/` — اگر معماری فعلی الزام کرد promptها اینجا باشند، فایل‌ها باید با نام واضح مربوط به `buti_ai` ساخته شوند و از داخل `giso/buti_ai/` مصرف شوند.
- `giso/beauty_centers/` — فقط برای center listing، خدمات، گفتگو و رزرو؛ منطق آینه زیبایی به این ماژول منتقل نشود.
- `giso/wallet*` — فقط برای هزینه/اعتبار احتمالی مراحل بعد.
- `giso/panel_user/` — فقط برای نمایش تاریخچه و نتیجه در آینده، نه مالک منطق آینه.
